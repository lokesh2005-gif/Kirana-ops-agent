# Kirana Ops Agent — Spec
 
Interface: Telegram only. No web UI, no admin panel, no forms — the chat IS the product.
 
## Domain
Indian kirana/supermarket, currency INR.
- Real SKUs (Aashirvaad Atta 5kg, Tata Salt 1kg, Amul Butter 100g, Fortune Sunflower Oil 1L,
  Maggi 70g, Parle-G, Surf Excel) + loose items (sugar/rice/dal by weight).
- Units: kg, g, litre, ml, packet, dozen, piece. Loose vs packaged.
- GST: per-item slab (loose staples 0%, packaged staples 5%, FMCG 12-18%), intra-state
  CGST+SGST split, each item has an HSN code, bill shows tax breakup, correct rounding.
- Payments: cash / UPI / card, with a reference field. No real gateway.
- Khata: customer credit ledger (add credit, record payment, check balance).
- Stock: cost price, sell/MRP price, quantity, reorder level. Selling decrements atomically.
 
## Capabilities (the model decides which tools to call — these are NOT fixed commands)
Receive stock · add product · cut a multi-item bill (multi-turn draft, editable, finalize) ·
stock query · low-stock/reorder alert · khata credit/payment/balance · daily close
(totals, tax collected, cash vs UPI, top items) · PDF invoice on demand · PPTX sales
analysis deck on demand · set/get a standing preference (default payment mode, default
brand, shop name/GSTIN for invoices).
 
Ambiguous requests (e.g. "add atta") get a clarifying question **generated by the model**,
not a hardcoded branch.
 
## Hard requirements (this is what's actually graded)
1. **Grounding** — prices/GST/stock always come from tools/DB. Never invented by the LLM.
2. **Oversell guard** — stock can never go negative; enforced at the DB/tool layer, not the prompt.
3. **GST correctness** — per-item slab, CGST/SGST split, correct rounding, legible breakup.
4. **Multi-turn bills** — a bill builds over several messages, is editable, and stock is
   only decremented on finalize (not while it's a draft).
5. **Idempotency** — Telegram redelivers updates; a retried "finalize" must not double-bill
   or double-decrement stock.
6. **Concurrency** — two simultaneous stock-affecting operations must not corrupt stock.
7. **Guardrails** — no selling below cost, no deleting stock, no settling a nonexistent khata,
   confirm-or-refuse rather than guessing.
8. **Real artifacts** — actual generated PDF invoice and PPTX deck with real charts from
   real DB data — not screenshots, not plain text pretending to be a document.
9. **Durable memory** — standing preferences persist across a Telegram /new and an app
   restart. Lives in the DB, not the conversation.
 
## Architecture requirements
- Agent-first: natural language → LLM → tool calls → LLM continues → response. NOT a
  regex/keyword router, NOT an if/elif intent tree, NOT a node-per-command state machine.
- Business rules (oversell, GST math, idempotency, khata rules) live in tools/services/DB,
  never only in the system prompt.
- Real control loop: observe → reason → act (tool call) → feed result back → continue,
  chaining multiple tool calls in one turn as needed.
- Persistence: SQLite (or Postgres), survives restarts.
